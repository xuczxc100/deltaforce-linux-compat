# 2026-11-21：啟動器空白與恢復紀錄

狀態：本機已恢復啟動，實際觀察到遊戲主介面，使用者回覆「已正常」。根本原因尚未完全隔離，不能據此保證每次冷啟動或長時間遊玩的穩定性。

本紀錄由 AI 協助整理；僅記錄實際執行的操作與觀察，不附原始日誌、帳號資料或遊戲檔案。

## 問題與先前狀態

使用者回報：先前已能進入大廳或實際遊玩，之後無法再次開啟。先前自動化觀察僅確認到首次設定畫面，因此後續將使用者回報與直接觀察分別記錄。

排查發現：

- 原有應用程式捷徑仍指向舊瓶子，沒有使用修改過的 GE 環境。
- 改用測試環境後，啟動器仍曾停在隱藏或空白的 510 × 800 視窗。
- 啟動器日誌曾記錄找不到 `Tahoma, sans` 字型。
- 使用原本 Wine runner 做對照時，ACE 顯示無法載入驅動程式，錯誤碼為 `1-1720-2000015145`。
- 先前遊戲日誌另有進入 `Iris_Entry` 後的致命錯誤；不能直接認定它與空白啟動器是同一個問題。

## 排查結果

安裝官方 x86／x64 Visual C++ v14 執行庫（14.52.37029）並未讓當時的空白啟動器恢復。重建網頁與 GPU 快取、試驗執行庫載入順序、停用啟動器的 DXVK／VKD3D，也未在各次測試中恢復正常介面。沒有改善的載入順序與繪圖設定已撤回。

登錄相容層另以直接匯出表查找方式重新驗證，結果為 **81 項檢查、0 項失敗**。此結果只涵蓋元件行為，不能代替遊戲啟動驗證。

曾比較主要 DLL 載入情況與憑證相關追蹤，但沒有足夠證據將憑證或網路認定為原因。

## 成功恢復的組合

1. 從實驗瓶子建立獨立的還原測試副本，保留既有相容性修正與 ICU 檔案。
2. 套用這輪執行庫修復之前備份的 `system.reg`、`user.reg`；這是重開失敗後、進一步修復前的備份，並非完整的「成功當下」快照。
3. 將 VC 執行庫 DLL 家族還原為原始瓶子的對應檔案。未改動原始瓶子的檔案。
4. 從同一套私人 Wine runner 的 `share/wine/fonts` 複製 `tahoma.ttf`、`tahomabd.ttf` 到還原副本的 `C:\windows\Fonts`。
5. 透過官方 Garena 啟動器啟動遊戲，沒有直接執行遊戲 EXE 來替代正常登入流程。
6. 將本機捷徑改為選用成功啟動的還原副本；下次啟動的 Wine 日誌設定恢復為 `-all`。

在補入字型後，啟動器正常顯示 1400 × 720 主介面與「啟動遊戲」按鈕。不過這次同時包含登錄檔與執行庫狀態還原，**尚未以單一變因測試證明字型是唯一原因**。

字型複製工具只使用已安裝 runner 隨附的檔案，不下載或發布字型，也拒絕覆蓋內容不同的同名字型。停止實驗瓶子後可執行：

```sh
python3 tools/install_launcher_fonts.py /path/to/private-runner /path/to/experimental-prefix
```

這個工具不是完整環境還原程式。不要將其他瓶子的登錄檔或執行庫直接套入自己的日常使用環境。

## 驗證與剩餘問題

直接觀察到的恢復流程是：Garena 啟動器正常顯示 → 遊戲預載資源 → 登入後公告 → 遊戲主介面。使用者隨後確認正常，遊戲保留執行供使用者操作。

字型工具已在缺少字型的瓶子執行，複製兩個檔案；在已有相同字型的還原副本重跑時複製零個檔案，沒有覆寫既有檔案。

下列事項仍未由本次恢復測試確立：

- 多次完整關閉後重新啟動的成功率。
- 線上對戰與長時間遊玩的穩定性。
- `Iris_Entry` 致命錯誤的原因與是否已排除。
- 仍出現在診斷日誌中的未實作 API，例如 `InbvAcquireDisplayOwnership` 與 `__CxxFrameHandler4`，對後續流程的影響。
