# 2026-11-21：啟動器空白與恢復紀錄

狀態：本機已恢復啟動，實際觀察到遊戲主介面，使用者回覆「已正常」。根本原因尚未完全隔離，不能據此保證每次冷啟動或長時間遊玩的穩定性。

本紀錄由 AI 協助整理；僅記錄實際執行的操作與觀察，不附原始日誌、帳號資料或遊戲檔案。

## 環境

| 項目 | 設定 |
|---|---|
| 平台 | Linux，透過 Bottles 執行 Garena PC 版 |
| Runner | GE-Proton11-12 x86_64 的獨立修改副本 |
| Wine 模式 | `WINEARCH=wow64` |
| 同步 | `WINEESYNC=0`、`WINEFSYNC=0` |

WFP 診斷模組仍回傳 `STATUS_NOT_SUPPORTED`，沒有因此新增封包過濾或完整反作弊功能。

## 問題與先前狀態

使用者回報：先前已能進入大廳或實際遊玩，之後無法再次開啟。先前自動化觀察僅確認到首次設定畫面，因此後續將使用者回報與直接觀察分別記錄。

排查發現：

- 原有應用程式捷徑仍指向舊瓶子，沒有使用修改過的 GE 環境。
- 改用測試環境後，啟動器仍曾停在隱藏或空白的 510 × 800 視窗。
- 啟動器日誌曾記錄找不到 `Tahoma, sans` 字型。
- 使用原本 Wine runner 做對照時，ACE 顯示無法載入驅動程式，錯誤碼為 `1-1720-2000015145`。
- 先前遊戲日誌另有進入 `Iris_Entry` 後的致命錯誤；不能直接認定它與空白啟動器是同一個問題。

## 排查結果

安裝官方 x86／x64 Visual C++ v14 執行庫（14.52.37029）並未讓當時的空白啟動器恢復。重建網頁與 GPU 快取、試驗執行庫載入順序、停用啟動器的 DXVK／VKD3D，也未在各次測試中恢復正常介面。沒有改善的載入順序與繪圖設定已撤回。

登錄相容層另以直接匯出表查找方式重新驗證，結果為 **81 項檢查、0 項失敗**。此結果只涵蓋元件行為，不能代替遊戲啟動驗證。

曾比較主要 DLL 載入情況與憑證相關追蹤，但沒有足夠證據將憑證或網路認定為原因。

## 成功恢復的組合

1. 從實驗瓶子建立獨立的還原測試副本，保留既有相容性修正與 ICU 檔案。
2. 套用這輪執行庫修復之前備份的 `system.reg`、`user.reg`；這是重開失敗後、進一步修復前的備份，並非完整的「成功當下」快照。
3. 將 VC 執行庫 DLL 家族還原為原始瓶子的對應檔案。未改動原始瓶子的檔案。
4. 從同一套私人 Wine runner 的 `share/wine/fonts` 複製 `tahoma.ttf`、`tahomabd.ttf` 到還原副本的 `C:\windows\Fonts`。
5. 透過官方 Garena 啟動器啟動遊戲，沒有直接執行遊戲 EXE 來替代正常登入流程。
6. 將本機捷徑改為選用成功啟動的還原副本；下次啟動的 Wine 日誌設定恢復為 `-all`。

在補入字型後，啟動器正常顯示 1400 × 720 主介面與「啟動遊戲」按鈕。不過這次同時包含登錄檔與執行庫狀態還原，**尚未以單一變因測試證明字型是唯一原因**。

字型複製工具只使用已安裝 runner 隨附的檔案，不下載或發布字型，也拒絕覆蓋內容不同的同名字型。停止實驗瓶子後可執行：

```sh
python3 tools/install_launcher_fonts.py /path/to/private-runner /path/to/experimental-prefix
```

這個工具不是完整環境還原程式。不要將其他瓶子的登錄檔或執行庫直接套入自己的日常使用環境。

## 驗證與剩餘問題

直接觀察到的恢復流程是：Garena 啟動器正常顯示 → 遊戲預載資源 → 登入後公告 → 遊戲主介面。使用者隨後確認正常，遊戲保留執行供使用者操作。

字型工具已在缺少字型的瓶子執行，複製兩個檔案；在已有相同字型的還原副本重跑時複製零個檔案，沒有覆寫既有檔案。

下列事項仍未由本次恢復測試確立：

- 多次完整關閉後重新啟動的成功率。
- 線上對戰與長時間遊玩的穩定性。
- `Iris_Entry` 致命錯誤的原因與是否已排除。
- 仍出現在診斷日誌中的未實作 API，例如 `InbvAcquireDisplayOwnership` 與 `__CxxFrameHandler4`，對後續流程的影響。

若再次出現相同問題，應先保留這次可用環境的副本，再逐項比較字型、執行庫與登錄狀態。新增回報只需包含去識別化的錯誤與最後到達的畫面，不要公開原始啟動參數或完整日誌。

## 後續：進入對局時閃退與執行庫修復

使用者隨後回報進入對局、載入地圖時閃退。引擎日誌的致命錯誤時間為 **18:18:28（UTC+8）**；移除多餘瓶子的清理時間為 **18:19:56**。這次已記錄的崩潰早於清理操作，共用遊戲與啟動器路徑經檢查仍完整。

分析發現，多個遊戲相依 DLL 與同版本 ICU 需要 `VCRUNTIME140_1.dll` 的 `__CxxFrameHandler4`。還原副本當時使用的是 Wine 內建版本；其診斷日誌出現對 CRT 私有 API 的未實作呼叫。但這些訊息本身不足以證明就是主遊戲致命錯誤的唯一原因。

在備份現有執行庫與登錄檔後，執行下列修復：

1. 停止已閃退遊戲所屬瓶子殘留的背景程序。
2. 在同一個可用瓶子成功安裝官方 Microsoft **x64 Visual C++ v14 Runtime 14.52.37029**，不回退已補入的 Tahoma 字型。
3. 明確指定 `vcruntime140`、`vcruntime140_1`、`msvcp140` 為 `native,builtin` 載入順序。
4. 透過官方啟動器重開，並從執行中遊戲的模組映射確認載入瓶子 `system32` 的 Microsoft 執行庫。

安裝程式第一次在殘留背景程序仍執行時遇到提權子程序連線失敗；完整停止該瓶子的背景程序後，重新安裝以 `0x0` 結束。應以安裝日誌確認成功，而非只確認安裝程式曾被執行。

官方下載來源：[Microsoft Visual C++ Redistributable](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist/)。本專案不散布 Microsoft DLL 或安裝程式。

修復後直接觀察到重新載入地圖至 82%，使用者隨後回覆「正常了」。這是一次載入恢復與使用者確認，尚不足以保證完整對局或長時間穩定性。下次啟動已恢復 `WINEDEBUG=-all`，沒有中斷使用者當時正在執行的遊戲。

另將 `NtCreateRegistryTransaction` 的引用定位到遊戲附帶的 `WevtUtil.exe` 效能輔助程式。這項未實作 API 與其他輔助程序錯誤仍需分開調查；不能將所有日誌中的 `aborting` 都解讀為主遊戲閃退，也不能宣稱所有 Wine API 缺口已修復。

## 確認的五分鐘崩潰：缺少視窗 band 系統呼叫

後續再次閃退，證實先前「重新進入遊戲」與使用者短暫確認正常，不足以證明執行庫修復已排除原因。唯讀解壓三份本機 ACE 診斷檔後，得到一致的原始例外：

| 引擎首次時間（UTC+8） | 引擎致命錯誤時間 | 間隔 |
|---|---|---|
| 18:13:26.432 | 18:18:28.635 | 302.203 秒 |
| 18:24:55.261 | 18:29:55.279 | 300.018 秒 |
| 18:37:15.420 | 18:42:16.172 | 300.752 秒 |

三份診斷檔都是 `0x80000100`（Wine 未實作函式例外），例外位置皆為 `win32u.dll + 0x14554`。對照同一份 Windows DLL 的匯出入口 `NtUserGetWindowBand`（RVA `0x14540`）與 syscall 編號 `0x145a`，確認例外位於該 API 入口內。該輪較早出現的 `RtlVirtualUnwind2` 存取違規可能屬於後續崩潰處理，不能替代這個原始例外證據。

最後一個失敗回合沒有新增 NVIDIA 記憶體配置、映射或 Xid 錯誤，仍以同樣例外失敗。因此，前面確實存在的顯存錯誤並不能解釋全部閃退；降低顯存壓力也不能取代缺少 API 的修正。

診斷檔由 ACE 採集，並不單獨證明 ACE 主動終止遊戲，或證明 ACE 就是呼叫該 API 的元件。此處修正的是 Wine 的系統呼叫實作，沒有修改遊戲、ACE 或其驗證結果。

### 實作與驗證

新增 [window-band-compat](../window-band-compat/README.md)，在獨立 runner 的 Unix `win32u.so` 補入 x64 實作，驗證真實 Wine 視窗並回傳現有桌面 band。保留 Windows DLL 原本的 syscall 入口，同時修正底層參數長度，涵蓋一般呼叫與直接 syscall。

本機完成 **60 項檢查、0 項失敗**，包括跨程序視窗、錯誤處理、不可寫入輸出記憶體、輸出邊界與直接 syscall。由公開原始碼重建的 overlay SHA-256，與實際安裝版本完全相同。工具保留原有 native unwind entries，另加入編譯器產生的新函式 unwind entry。

修補後的進程已通過原先約 300 秒的失敗點，期間實際觀察到線上對局與 60 FPS 遊戲內讀值，該時間點沒有新 ACE 診斷檔。這是有限的本機實機驗證，不能擴大為所有 Wine 版本、32 位元呼叫或長時間穩定性的保證。

先前的日誌可能包含登入資訊；原始 dump、完整日誌與畫面沒有上傳。可用 [inspect_ace_dump.py](../tools/inspect_ace_dump.py) 在本機唯讀輸出例外碼、模組檔名及相對位移。
